## Context

Акт із `edo_provider = dubidoc` після класифікації відправляється в Дубідок (`POST /documents`, `workflowType: sequential`, `/send` НЕ викликається). За цим маршрутом **першим підписує власник документа — ФОП** (тримач `DUBIDOC_TOKEN`/`DUBIDOC_ORGANIZATION_ID`), і лише після цього публічне посилання на підпис стає потрібним клієнту (`participant`, `priority: 1`). Поточний стан акта в цей момент — `sent_to_edo` (`edo_status = new`).

Зараз єдиний спосіб поставити ФОПівський підпис — кнопка «Перейти в Дубідок» (`act-detail-panel.tsx`), що відкриває `my.dubidoc.com.ua/documents/{id}` у новій вкладці. Після підпису користувач вручну тисне «Оновити статус» (`refreshDubidocStatusAction`), який мапить `new → waiting_for_client_sign`.

Дубідок надає `POST /api/v1/documents/{id}/links { action: "sign" }`, що повертає `{ link }` — публічний URL сторінки підпису. Той самий механізм уже працює в проді в застосунку **zbory** (`components/vote/dubidoc-signing-widget.tsx` — простий `<iframe src={link}>`; `lib/dubidoc/real-provider.ts` — `generateSigningLink`). Уся криптографія (ІІТ/Дія/Mono/SmartID) виконується всередині сторінки Дубідок у iframe.

Наш HTTP-клієнт (`lib/external-apis/dubidoc/client.ts`) уже автентифікується тими ж заголовками (`X-Access-Token`, `X-Organization`) і має retry/429-логіку — нові виклики переюзають `attemptRequest`.

## Goals / Non-Goals

**Goals:**

- Дати ФОПу поставити власний підпис на акт у модалці з iframe, не покидаючи сторінку деталей.
- Переюзати наявний `refreshDubidocStatusAction` для оновлення статусу після підпису (без нової логіки статусів).
- Мінімізувати вікно дії публічного sign-посилання: відкликати його одразу після підпису.
- Лишити завантаження в Дубідок без змін: «просто завантажити» і «завантажити + підписати» — обидва сценарії живі.

**Non-Goals:**

- Власна криптографія підпису (euscp/ІІТ-бібліотека, прямий `POST /documents/{id}/sign`) — НЕ робимо; це робота, яку віддаємо UI Дубідок в iframe.
- Підпис клієнта в нашому додатку — поза скоупом; клієнт підписує віддалено за листом-посиланням Дубідок.
- Зміни в `send-to-dubidoc.ts`, схемі БД, мапінгу статусів (`dubidoc-status.ts`), polling-кроні.

## Decisions

### D1. Iframe + публічне sign-посилання (підхід A), а не прямий `/sign` API

`POST /documents/{id}/links { action: "sign" }` → `{ link }` → `<iframe src={link}>`. Альтернатива (`POST /documents/{id}/sign { signature: base64 }`) вимагає вбудувати euscp/ІІТ-бібліотеку, обчислювати хеш `document.file`, самостійно вести хмарні флоу Дія/SmartID/Mono — фактично перебудувати сторінку підпису Дубідок. Підхід A доведений у проді в zbory і дає всі методи підпису безкоштовно. Обираємо A.

### D2. Server action генерує посилання, клієнт лише рендерить iframe

`getSigningLinkAction(actId)` (server) валідує, що акт належить додатку, має `edo_provider = dubidoc`, `edo_doc_id` і статус `sent_to_edo`, потім викликає `generateSigningLink(edo_doc_id)` і повертає `{ url }`. Токен Дубідок ніколи не потрапляє в клієнт. Клієнтський компонент `dubidoc-signing-widget.tsx` отримує лише `url` і показує `<iframe>`.

### D3. Відкликання посилання + оновлення статусу при закритті модалки

Дубідок не шле нам подію «ФОП підписав» у цей UI-флоу. Тому при натисканні «Готово / Закрити» в модалці викликаємо `revokeSigningLinkAction(actId)` (→ `DELETE /documents/{id}/links`) і одразу `refreshDubidocStatusAction(actId)` + `router.refresh()`. Якщо статус перейшов у `waiting_for_client_sign` — підпис відбувся; якщо лишився `sent_to_edo` — ФОП закрив, не підписавши (посилання все одно відкликане, наступний клік згенерує нове, бо для `action=sign` Дубідок повертає те саме посилання, а після DELETE — нове).

Альтернатива (полінг статусу в модалці кожні N секунд) відкинута як надмірна для MVP — підпис ФОПа синхронний, користувач сам закриває модалку, коли завершив.

### D4. «Підписати тут» поряд із «Перейти в Дубідок», умова показу як у наявних кнопок

Кнопку показуємо за тих самих умов, що визначають `showDubidocLink`/`showRefresh` у `act-detail-panel.tsx`: `edo_provider = dubidoc`, статус `sent_to_edo`. «Перейти в Дубідок» лишаємо як fallback (на випадок, якщо iframe заблоковано — див. R1).

### D5. CSP `frame-src` для домену Дубідок

iframe вимагає, щоб наш CSP дозволяв фреймити домен Дубідок. Зараз CSP явно не налаштований (`next.config` без headers). Додаємо `frame-src` із доменом сторінки підпису Дубідок. Точний домен (`*.dubidoc.com.ua`) фіксуємо за результатом spike R1.

## Risks / Trade-offs

- **R1 — Дубідок може забороняти вбудовування в iframe** (`X-Frame-Options: DENY` / `frame-ancestors` без нашого домену) → Spike перед UI-фіналізацією: згенерувати sign-посилання і відкрити в iframe локально, перевірити заголовки відповіді Дубідок. zbory фреймить у проді (публічна сторінка) — прецедент позитивний. Mitigation, якщо заблоковано: лишаємо «Перейти в Дубідок» (вже є) як основний шлях і документуємо обмеження.
- **R2 — Публічне sign-посилання доступне будь-кому з URL** → Вікно мінімізуємо: посилання живе в межах однієї модальної сесії і відкликається через `DELETE /links` одразу при закритті. URL видно лише автентифікованому адміну в iframe, у DOM не логуємо.
- **R3 — Користувач закрив модалку, не підписавши** → `refreshDubidocStatusAction` лишить статус `sent_to_edo`; посилання відкликане; повторний клік «Підписати тут» згенерує нове посилання. Жодного «застряглого» стану.
- **R4 — `DELETE /links` відкликає ВСІ посилання документа** (за докою — «абсолютно всі попередньо згенеровані посилання»), включно з `view`-посиланнями, якщо такі колись генеруватимуться → Зараз ми генеруємо лише `sign`-посилання, тож побічних ефектів немає. Якщо в майбутньому зʼявляться `view`-посилання — переглянути стратегію revoke.
- **R5 — Подвійний рендер модалки / повторний клік** під час генерації посилання → кнопка з `loading`-станом (як наявні кнопки в `edo-controls.tsx`), iframe монтується лише після отримання `url`.

## Migration Plan

Без міграцій БД. Деплой звичайний (dev → prod гілки Neon не зачіпаються, бо схема не змінюється). Rollback — revert коміту; наявний шлях «Перейти в Дубідок» лишається робочим увесь час, тож фіча адитивна й безпечна.
