## Context

`/acts/new` — server component, що читає БД (контрактні клієнти) без жодного dynamic API: auth живе у `proxy.ts` і не робить сторінку динамічною. Next 16 пререндерив сторінку під час білда (`○ Static` у route table), тож пікер віддавав знімок БД з моменту деплою. Паралельно дані: 243/429 клієнтів мають порожній `name` (MoeOSBB-дублікати без юр. назви), частина з них архівні (`auto_act_disabled`), але мала договори (бекфіл 2026-06-01, номер договору = MoeOSBB ID) і потрапляла в пікер, дублюючи ЄДРПОУ. Лейбл рендерився як `name (legalId)` → «(42953700)» для порожніх назв.

`ClientCombobox` — спільний компонент трьох поверхонь: створення ручного акту, редагування акту (read-only), розділення платежу.

## Goals / Non-Goals

**Goals:**

- Живий список клієнтів у пікері на кожен запит.
- Жодних архівних/сміттєвих дублікатів у пікері ручного акту.
- Читабельний лейбл рядка незалежно від якості даних: коротка назва → «Договір №X» → ЄДРПОУ → «—».
- Пошук знаходить клієнта за будь-яким ідентифікатором: повна назва, коротка назва, ЄДРПОУ, № договору.

**Non-Goals:**

- Чистка сміттєвих договорів/клієнтів у БД (окрема data-робота).
- Динамізація статичних сторінок `(settings)` (той самий клас бага, але дані мутуються через actions на самій сторінці).
- Зміна семантики класифікації (`auto_act_disabled` досі матчиться) і split-обмежень по платнику.

## Decisions

- **`export const dynamic = "force-dynamic"`, а не `connection()`/`noStore()`**: маркер на рівні route — найпростіший і видимий у route table; на сторінці немає кешованих піддерев, які варто було б зберегти.
- **Виключення архівних тільки в пікері ручного акту**: у split-формі архівний клієнт може бути легітимним платником (класифікація матчить `auto_act_disabled`-клієнтів — спец. рішення в `specs/classification`), тож там список не звужуємо.
- **Лейбл без повної юридичної назви** (рішення користувача): коротка назва — кураторське поле саме «для списків»; повна назва занадто довга для рядка дропдауна. Fallback «Договір №X» працює завжди (inner join гарантує договір), ЄДРПОУ — страховка для read-only режиму редагування (left join). Повна назва лишається в haystack пошуку.
- **`clientLabel` у `lib/acts/client-label.ts`**: чиста функція + тип `ContractClient` поза "use client"-файлом — тестується unit-тестами без підтягування server actions; форма реекспортує тип, тож імпорти споживачів не змінюються.
- **Сортування `nullif(short_name,'') nulls last, nullif(name,'') nulls last`**: порядок списку відповідає тому, що відображається; клієнти без короткої назви не «розчиняють» алфавітний порядок.

## Risks / Trade-offs

- [110 активних клієнтів з договором не мають короткої назви → показуються як «Договір №X (ЄДРПОУ)»] → пошук за повною назвою досі працює; лейбли виправляються наповненням `short_name` (кураторське поле картки клієнта).
- [force-dynamic прибирає будь-яке кешування сторінки] → сторінка адмінська, низькочастотна; вартість — один DB-запит на відкриття.
- [Архівні клієнти у split-пікері виглядають як дублікати ЄДРПОУ] → свідомий виняток, щоб не зламати split платежів від `auto_act_disabled`-клієнтів; зафіксовано в дельті specs.
