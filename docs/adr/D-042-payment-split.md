# D-042 — Розділення платежу на кілька актів (ручне)

**Дата:** 2026-05-31

**Переглядає:** D-007

**Рішення:** Вводиться **ручний** шлях розділення одного реального платежу на кілька актів.
Кожен акт вказує на той самий існуючий платіж (`acts.payment_id`), нові платежі **не**
створюються, і діє інваріант звірки `Σ(act.amount) == payment.amount`. Cardinality
`Payment ↔ Act` стає `1:N` для явно розділених платежів.

D-007 (1 платіж = 1 акт) лишається чинним для **автоматичної** класифікації: bundled-платіж
(одна сума за кілька послуг або за кілька ОСББ) автокласифікатор НЕ розщеплює — він і далі
потрапляє в чергу. Розщеплення — лише свідома ручна дія оператора.

**Альтернативи:**

- **Залишити лише D-007 (тільки черга).** Відкинуто: реальні bundled-платежі (доступ + СМС одним
  переказом; транзитний переказ за дві ОСББ — явно названий нерозвʼязним у D-027) не мають
  легітимного оформлення. Єдиний обхід — ручний акт із синтетичним `manual_external`-платежем на
  кожну послугу, що **подвоює** реальні гроші у списку платежів і відвʼязує акти від справжнього
  переказу.
- **Parent/child платежі.** Відкинуто: зберігає буквальне «1 акт = 1 платіж», але додає окрему
  сутність і платежі-привиди; складніше без виграшу в чесності обліку.
- **Один акт-пакет із кількома рядками послуг.** Відкинуто: модель акту одно-сервісна (один
  `service_type`/ціна/кількість, окремий PDF/шаблон на послугу), мульти-рядковий акт — велика
  переробка PDF і під питанням юридично.
- **Дозволити `Σ < payment.amount` (передоплата із залишком).** Відкинуто для v1: строге `==`
  тримає облік чесним; часткове розподілення — окремий майбутній сценарій.

**Обґрунтування:**

- Інваріант D-007 був спрощенням, яке переросли реалії «доступ + СМС одним платежем» і
  «дві ОСББ одним переказом».
- Схема вже це тримає: `acts.payment_id` — `NOT NULL`, але **без** unique-обмеження, тож кілька
  актів можуть посилатися на один платіж **без міграції**. `payments.act_id` лишається
  денормалізованим вказівником на перший акт; канонічний набір актів читається зворотним запитом
  `acts WHERE payment_id = …`.
- Авто-шлях незмінний — жодних «тихих» автоматичних розщеплень, які важко помітити постфактум
  (та сама мотивація, що в D-027).

**Наслідки:**

- Cardinality `Payment ↔ Act` = `1:N` для розділених платежів (`1:1` лишається нормою авто-шляху).
- Нова здатність `payment-split`: форма на N рядків, звірка `Σ == amount`, привʼязка до існуючого
  платежу, доступність зі станів `received`/`awaiting_review`/`in_queue`/`skipped`, оптова
  «Скасувати розділення».
- `skipped` більше не абсолютно термінальний: пропущений платіж можна розділити (перехід у
  `classified`). Скасування розділення повертає платіж до попереднього стану — `skipped`, якщо він
  був пропущений, інакше `received`.
- Розділені акти **не** редагуються/видаляються поштучно (шлях редагування/видалення ручних актів
  лишається обмеженим до `source = manual_external` і додатково блокується, коли платіж підтримує
  кілька актів) — зміна розділення лише через «Скасувати розділення» + повторне розділення.
- **Міграція БД не потрібна.**
- Non-negotiable constraint у `openspec/project.md` переформульовано з «One payment ↔ one act … No
  bundling, no split» на інваріант `Σ(act.amount) == payment.amount` для ручного розділення.
